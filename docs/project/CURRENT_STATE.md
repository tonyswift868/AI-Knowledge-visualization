### [ARCH-06] 新建计划的编排流程
- 状态：已实现，待用户验收
- 1 表单：AI 第一条消息就是表单卡片（固定内容，不调模型）：学习目标、最终目标、起止日期、这份计划每天最多学多久、每周哪几天能学、特殊日（日历点选没空/半天）、当前水平（预设 + 补充说明）、是否只用自己的资料。
- 2 需求核对：必填项缺失由宿主直接判定；需求核对 agent 返回“够不够 + 最多 3 个追问 + 规范化目标”。对话里的其他说法由意图理解 agent 分类处理（改表单、限定章节、按名字/序号处理资料、删移模块、提问）；付费和开始仍需点按钮（BUG-13）。
- 3 资料：厂商自带搜索 → 过滤（T04）→ 逐个打开核实并提取正文 → 规则评分 + 模型复核（PLAN-06）→ 资料卡片由用户采用/不要；“再找找”先展示上轮未展示的，再换思路重搜；用户上传的文件和贴的网址（含 GitHub 仓库）直接提取、默认采用；“只用我的资料”则跳过搜索。
- 4 轮廓：只读资料标题、目录和摘要，给出阶段 → 模块（依据哪些章节、前置模块、时长区间）；宿主按每点约 15 分钟推点数，再用与正式生成相同的公式加上模块检测和最终检验时长，给出总时长和每天分钟范围并对照上限提醒（PLAN-05）；用户在聊天里提修改，直到点“正式生成”。
- 5 正式生成：先显示 token 预估（SYS-03）；每个模块一个生成 agent、并发 4 个，只读该模块的资料块（全文分批，截断拆半，BUG-15），每点带出处块、约 15 分钟；出处必须来自提供的块；单模块失败可单独重试。
- 6 生成后未开始：可删模块、调顺序（不能排到依赖模块之前），超上限可一键延后结束日；点“开始计划”后进入进行中（重复点击安全，BUG-29）。
- 当前实现：app/plan_flow.py（编排）+ course/planner_agents.py、plan_intent.py、research_pipeline.py、source_quality.py + 页面 web/src/pages/NewPlan.tsx。
- 验证：2026-09-27 真实全链路（82 个点、约 2.5 分钟）；两次小测试都从这里开始建计划（QA-01）。

### [PLAN-01] 对话中收集需求，缺信息时 AI 反问

### [PLAN-02] 先出计划大致样子，用户满意后正式生成

### [PLAN-04] 知识结构：阶段 → 模块 → 知识点
- 状态：已实现，待用户验收
- 需求：不要把几千个知识点平铺给用户。分成几个阶段，每阶段若干模块；模块按知识本身的结构划分，不按分钟数切。每天学多少不按模块数定，见 PLAN-05。
  - 知识点按学习量切（2026-09-29 用户定）：一个点约 15 分钟学习内容（可含几个小要点），不设整份计划的点数上限（例如背一万个单词的计划点数自然多）。约 15 分钟只是整份计划的平均数，单个点可以 2 分钟也可以 50 分钟，按内容难度估，不设任何上下限、不自动拆点（2026-10-02 用户定）；现在程序把每点限在 10–20 分钟（planner_agents.py 第 611 行）、超了整个模块生成失败，要去掉。用户不能规定每模块几个点这类结构（结构由系统按资料定），第三十批“按补充说明凑点数”要去掉。
- 知识点从资料中提炼：先有资料，再从资料里提炼模块和知识点，每个知识点天然带出处；不允许先凭空生成知识点再找资料匹配。资料覆盖不到的内容说明资料不够，应在轮廓阶段继续找资料（PLAN-06）。

### [TEACH-04] 独立判定 agent，贯穿整个计划
- 状态：五类题型与逐条判法已实现（第二十六批）；自建中文样例全对，公开数据集一致 82%，对简略作答偏严，待校准
- 需求：讲课的老师只管讲；“懂没懂、过没过”由单独的判定员依据用户实际作答判定，不看用户自称。判定员贯穿整个计划：随口问、模块检测、最终检验、自由检验，出过的错都记下来。冤枉必须零次（QA-01）。
  - 主观题（简答，2026-09-29～30 用户定）：参考答案的必答要点拆成一条条“答到了吗”，全部答到才算对；简答题每题只问 1–2 个要点。判定员只看题目、必答要点和这一次的回答，不看对话；学生的“我肯定对”之类当作普通文字。依据不要求逐字引用学生原话，同义说法同样算。判定员拿不准时，针对同一个知识点再问一道更深的题：答错记错，答对记对。
  - 选择题由程序判，不用模型。
  - 多个知识点合在一题时，判定员分析错在哪个点，只给那个点记错。
  - 题型与判法（2026-10-01 用户要求：简答难判不能靠少出简答来回避，每类题都要有判法。用户认可下面的方案，但必须经过检验才算数；随口问不出论述题，用户确认）：
    - 有确定答案的题（填空、计算、写式子、说出名称）：出题时写标准答案和允许的等价写法（数值误差、等价式、同义名称）；先由程序比对，程序判不了才交判定员；过程题按下面的规则。
    - 简答题（解释为什么、说明区别、举例）：必答要点 1–2 条，每条必须是一个能单独判断对错的说法，并写明算对的说法（意思对即可）和算错的说法（常见误解）；题面必须明确问到每一条要点。判定逐条给“答到 / 没答到 / 说错了”，全部答到且没有说错才算对，理由引用学生原话。
    - 论述题（评价、比较、分析）：出题时写 3–4 项评分细则（例如核心观点、依据资料的论据、推理连贯、没有事实错误），每项写清“达到”的标准；判定逐项给结论并引用原话。建议通过线：核心观点和“没有事实错误”必须达到，其余至少达到一项；只在模块检测和最终检验里、学科适合时出，随口问不出。
    - 题型比例保持现在（约六七成选择题），不为省事减少简答。
    - 判定回归：每类题备一套标准作答样例（对的、部分对、常见错、换了说法的），每次改判定都离线回放。
    - 依据（2026-10-01 架构师查阅开源项目与文献）：按题目单独写的评分细则比通用细则判得准（Rubric Is All You Need，2025）；逐条“达到 / 没达到”这种二选一的判法与人工最一致，细则分档越细越不准，把拿不准的挑出来另行处理能提高其余的准确率，对同义改写比较敏感（Rubric-Conditioned LLM Grading，2026）；“先定细则、再判、判完复核”三步（Grade Like a Human，2024）；根据判错的样本自动改评分指引（GradeOpt，2024）；开源评审模型 Prometheus 用“细则描述 + 每档描述 + 参考答案”的格式，与人工评分相关 0.897。开源实现可参考 microsoft/LLM-Rubric、The-LLM-Data-Company/rubric、llm-rubric-evaluation-harness（逐条给理由，并检验评审本身可不可信）。

### [TEACH-06] 讲课形式、随时插话、防用户带偏
- 状态：引导式分步课堂已实现（第二十五批，离线测试通过；界面只用假数据核对过），真实课堂未验证
- 需求：
  - 快速推进、引导式（2026-10-01 用户定，核心要点）：老师有备好的讲稿，但不是只把稿子发给用户；要依据讲稿引导用户，对话顺畅，快速把这个知识点拿下。默认（用户没调偏好时）推进节奏偏快、不拖沓；AI 本来回答就慢，再慢吞吞用户会觉得程序有问题、感觉不到学习提效。做法见下面“课堂方案”。
  - 一个知识点一个知识点地讲；讲完只随口问一个问题。问题可以简单，但不能糊弄；真正暴露问题靠模块检测。
  - 篇幅可以设软上限，但某个点确实需要讲很长时必须讲完，绝不能讲到一半断掉。
  - 讲得鲜活：优先用生活中的例子类比，不能一直念资料原文；可按用户偏好领域举例，但套不上就不硬套。
  - 讲到的内容标注出处，用户可点开看原文；需要时显示公式、代码、表格（与主题无关时不放代码，见 TEACH-08 待修）。
  - 语言：老师一律用中文讲；引用英文原文时附中文解释；出题用中文，关键术语保留英文。
  - 用户可随时插话提问（哪怕题外话），老师答完回到原进度。
  - 防用户带偏（项目重点）：计划、检验规则、进度判定不受聊天内容改变。老师没有改状态的权限；用户要求“删检验/直接让我过”，老师只解释并指向正规入口（如“我的计划”）。
  - 随口问答错：老师换个角度再讲一遍、给个台阶；用户说是误触也可以继续，但一律记一次错。
  - 判定之前老师绝不能透露答案或提示（包括闲聊、插话后把话题拉回原题时）；判定之后可以讲答案（2026-09-30 用户定）。随口问只是简单确认，可以直接问刚讲过的内容，或只做一点点变化，不必专门换角度出题（2026-10-01 用户定，取代原先“不能和讲稿例子原样相同”的限制）；备课和讲稿核对都不再因“与讲解或例子重复”要求修改。
- 当前实现：app/classroom.py：讲稿按步出（classroom.next 继续、classroom.choose 选引导选项后立刻出备好的回应、讲解中打字插话由老师现场接、classroom.back 回到刚才）；随口问答对只显示“答对了”并进下一点，答错老师一两句纠正再出备好的第二道（题面和参考答案一起换）；没有核对过的讲稿时现场分 2–3 小段讲并记 live（TEACH-08）。界面 web/src/pages/Classroom.tsx + web/src/classroom/GuidedLesson.tsx（第 N/M 步、继续、选项、回到刚才，按钮防重复，回车继续）。判定前老师回复先缓冲，程序检查是否含参考答案要点，含则重写一次，还不行只重述题目（BUG-32）；想改规则时分类为 change_rules，老师解释并指向「我的计划」；老师在不该出题的步骤自己加的问题并入讲解（BUG-19）。

### [CHK-01] 首轮学完后的最终检验、题库与计划画像
- 状态：第二十五批已改（离线测试通过）；真实出题合格率 61.5% 未达标；真实最终检验未验收
- 需求：整个计划第一轮学完后统一进入“检验”（不叫复习）。
  - 覆盖：所有知识点都要检验，不能只抽查；模块检测里错过的点多出题。
  - 过关等级（2026-09-29 用户定，已实现）：升到 3 级过关。随口问和模块检测都对 → 起始 2 级，答对 1 次过；只错过随口问、模块检测对 → 2 级，答对 1 次过；模块检测错过（不论随口问）→ 起始 1 级，要连续答对 2 次；最终检验中任何一次答错 → 退回 1 级，再连续答对 2 次。同一个点答对后不紧接着再问，每次换没用过的角度。

### [BUG-38] 输出上限包含思考导致整次作废；后台调用超时
- 状态：已修（2026-10-01，离线验证）
- 现象：第二次小测试 13 次输出撞上限整次作废（已知白花 ¥0.47），两点一批出题有一半被截断；讲稿核对 9 次超时，拿不到用量。
- 原因：厂商把思考算进输出上限，老师 4096、判定 4096、档案 2048、出题 8192 都不够；时限是整次请求的总时限，后台高强度思考调用和前台共用预设的 60 秒。
- 排查：架构师按用途统计截断调用的输出与正文长度、核对调用耗时。
- 解决：25-MF02：按用途抬高输出上限下限、后台用途时限 240–300 秒、拿不到用量的调用记为“用量未知”（SYS-01、SYS-03）。
- 验证：离线测试覆盖只抬不降、后台时限、未知用量计数与显示；25-MF03 真实出题 5 批截断 0。
- 经验：上限只是封顶，调高不多花钱，截断才白花。
- 关联：[SYS-01] [SYS-03] [BUG-36]
- 更新：2026-10-01
