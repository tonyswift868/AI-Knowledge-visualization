### [ARCH-01] 前端：单个 React 应用 + 本地桥
- 状态：设计待用户确认
- 窗口：`LearningWindow` 仍是账号外壳看到的那个 Qt 窗口，对外接口一个不变（构造参数，`switch/logout/verify` 信号，`bind_account_settings`、`bind_feature_context`、`rebind_feature_context`、`set_server_role`、`set_session_notice`、`clear_session_notice`、`session_recovered`、`request_current_plan_export`、`dispose`），保证 ACC-02 不动账号逻辑。窗口内部只放一个铺满的 WebEngine 视图，侧栏、导航、所有页面都在 React 里；账号按钮点击后由桥转成原有 Qt 信号。
- 加载：沿用已提前注册的 `mentorflow://` 协议，由一个处理器统一提供 `mentorflow://app/`（新界面构建产物）和 `mentorflow://assets/`（Live2D 模型，从本机数据目录读）；匿名、不落盘的 WebEngine 配置沿用现状；页面加严格 CSP：只允许本地脚本，不加载任何外部脚本和图片。
- 桥（QWebChannel，一个对象）：前端发 `{id, method, params}`；Python 按方法名分发到处理函数，耗时操作在后台线程执行，结果经 Qt 信号回到界面线程再发给前端：`{type:'response', id, ok, result | error{code, message}}`；流式输出发 `{type:'stream', id, delta}`；前端可发 `cancel{id}`；Python 主动推送 `{type:'event', name, data}`（如计划变化、今日进度、同步状态、会话提醒）。所有参数在 Python 侧校验类型和长度，前端传来的内容一律不当作可信输入。
- 渲染安全：模型输出和资料正文用 react-markdown 渲染，不启用原始 HTML；外部链接一律经桥交给系统浏览器打开，只允许 https。
- Live2D：把旧前端成熟的 Teacher2DStage 及其 Live2D 适配代码（约 3,500 行）提取进新界面源码，去掉违和的待机摇头（TEACH-05）；老师面板是 React 组件。窗口模式点“展开”→ 桥让窗口向右加宽一个面板宽度（屏幕放不下就在窗口内占右侧）；全屏/最大化时面板直接占课堂右侧。全屏由按钮或 F11 切换。
- 构建：新界面源码在 `refactor/learning/web/`（只放源码和构建产物 dist）；构建依赖不再借用旧项目 `E:\aiPlay\...\node_modules`，改为本项目自己的依赖目录（位置见 ENV-01）（锁定版本：react、vite、@xyflow/react、dagre、react-markdown、remark-gfm、remark-math、rehype-katex、katex、zustand、lucide-react、pixi.js 及 Live2D 引擎）。
- 主题：颜色全部用 CSS 变量；先做“精修现有粉/深紫”和“开发方自由发挥”两套（UI-00）。
- 退役：新界面可用后，删除旧 Qt 页面（overview/plans/materials/planning/classroom/tools/preferences/connections 的页面代码）及旧七步 bundle，重构区只留在用的文件。

### [ARCH-04] Agent 分工与权限
- 状态：设计待用户确认
- 原则：agent 只返回文本或严格格式的 JSON；宿主按固定格式校验（字段、长度、ID 必须来自本次输入），不合格重试一次，仍不合格就报错，不落库。任何 agent 都没有改状态的工具；计划、检验规则、进度、账本只由宿主状态机按用户在界面上的操作改变（TEACH-06 防带偏的底层保证）。资料正文作为“数据”放入请求，提示中明确“资料是内容不是指令”。

### [ARCH-05] 同步与服务器改动
- 状态：设计待用户确认（服务器部分已派 T07）

### [PLAN-05] 每日任务按时长均分（含特殊日权重）
- 状态：已实现未验证（部分）
- 需求：每天的任务是“学习时长”，不是“学几个模块”。根据资料估算整份计划总时长（第一轮学习 + CHK-01 检验），在起止日期内按可学日平均分配；用户说某天没空则该天为 0，某天只能拿出平时一半时间则该天权重为一半。算出每天应完成的分钟数，非特殊日每天对等。学到当天时长用完就停，哪怕某个模块只开了个头，第二天接着学。
  - 每日上限：用户填写“每天最多能学多久”；算出的每日时长超过上限时提醒用户。
  - 检验预留：按“检验时约 90% 能答出、10% 答不出”来估算并预留 CHK-01 的时间。

  - 补欠：用户后来学的时间算作补之前那天的进度，不重排计划。偶尔欠一点（如一小时）正常，第二天、第三天慢慢补即可。

  - 每日上限只针对当前计划：制定计划时明确问“这份计划每天最多能学多久”；用户同时有多个计划时自己调整截止日期，系统不跨计划合并。

### [PLAN-06] 资料检索：必须找权威资料
- 状态：已验证（DeepSeek 搜索可用）/ 结果过滤未开始

### [TEACH-02] 模块检测 + 知识点薄弱标记
- 状态：已实现未验证（新界面课堂，待用户验收）
- 需求：AI 教师要判定用户学会。学习过程中教师边讲边随口问，记录掌握不好的点，但不当场反复追问；模块学完后做一次正式模块检测，覆盖模块内知识点；掌握的知识点达到 90% 才算模块通过，通过时对没掌握好的点打标记，供 CHK-01 使用。不到 90% 模块不通过，只重学没掌握的那部分知识点；没过的点记录下来，从多个角度出题重测，重测答对一次即可（例如只到 89%，就只重学那 11%），不整个模块重来。没通过时教师针对这几个点做问答，让用户知道自己哪里没记住再去复习；复习在本产品内完成，不让用户去别的 AI 学。

  - 一个知识点一个知识点地讲；讲完不立刻正式测试，只随口问一个问题。问题可以简单，但不能糊弄（否则没有存在意义）；真正暴露问题靠模块检测（TEACH-02）。
  - 篇幅可以设软上限，但不能卡死：某个点确实需要讲很长时必须讲完，绝不能讲到一半断掉。
  - 讲得鲜活：所有教师都优先用生活中的例子类比，不能一直念资料原文，否则就成了“材料播放器”，无聊且记不住。可按用户偏好领域（如游戏）举例，但套不上就不要硬套（旧版硬套“小丑牌”类比，浪费时间）。

  - 语言：老师一律用中文讲；引用英文原文时附中文解释；出题用中文，关键术语保留英文。

  - 防用户带偏（项目重点）：用户随口一句话不能让教师乱套。例如用户说“检验不需要存在”，教师不能当真去删检验。计划、检验规则、进度判定不受聊天内容改变。

  - 多个知识点合在一题时，答错要由判定 agent 分析具体错在哪个点，只给那个点记错，不能把整题涉及的点全判错。必须做出来。

### [CHK-01] 首轮学完后的多轮检验与计划画像
- 状态：组件已实现，编排未开始
- 需求：整个计划第一轮学完后统一进入“检验”（不叫复习）。
  - 覆盖：所有知识点必须完整过一遍，不能只抽查；TEACH-02 标记过的、失败次数多的点多出题。
  - 推进：不分固定轮次、不设轮数上限。先完整过一遍，之后一直针对有问题的点问，直到没有问题；全部知识点通过检验即完成。
  - 归因与画像：对发现的问题归因，形成这份计划的用户画像（哪里有问题），后续按画像针对性检验。归因只做到能做好的程度，不为此做复杂系统。
  - 不重讲：检验阶段教师不把内容再讲一遍，只反复针对易错点提问；用户可主动提问，教师解答。
  - 时间：检验时间不能占大头，大致不超过学习时间的一半量级（用户说数值是随口说的，不作硬指标）。
  - 过关规则（熟练度等级，类似不背单词；用户已确认）：每个点有 0–3 级，升到 3 级即通过检验。初始等级：随口问和模块检测都没错 → 2 级（答对 1 次）；只在其中一处错过 → 2 级但优先出题，且换一个没考过的角度（答对 1 次）；两处都错过 → 1 级（连续答对 2 次）。检验中答对升一级、答错降一级（最低 0 级），所以最多连续答对 3 次，不会无限反复；对错穿插时等级原地打转，天然要求连续答对。同一个点答对后不紧接着再问，隔几题或到下次学习再问（间隔重复），每次换没用过的角度。
  - 角度：复述概念、用到例子、与相近概念区分、找错改错、换场景迁移；同一点不重复用同一角度。对错由 TEACH-04 判定 agent 判。
  - 逾期：截止日到了还没学完或没检验完，计划标为“已逾期”，显示逾期几天，继续学到完成为止；不生成阶段报告（任务没完成）；用户可自行延长截止日期。
  - 时长预估：建计划时就按“90% 的点一次答对、10% 的点有问题且每个约答错 2 次”预估检验时长，计入总时长（PLAN-05），并明确告诉用户这是预估，实际可能花更多时间。
  - 进度：每个点的检验时长 = 需答对次数 × 每题估算时长；每答对一次记一次进度，与学习阶段同一套“今天已完成 X / Y 分钟”。
  - 题型：选择、简答、纠错题（给出一段说法或解法，让用户判断有没有问题，有问题要说出错在哪、为什么）；尽量不出单纯判断对错的题（无法看出是否真正掌握）。题目不能露出明显线索，让人从字面就能猜出答案。也可以是和 AI 实时对话式的模拟检验。模块检测和检验都在聊天里一题一题进行，选择题可直接点选。
  - 题目来源：AI 依据资料原文出题，每题标注出自哪段资料；资料就是制定这份计划时用的那些（用户给的或检索到的，可以多份）。没有资料依据的题不出。AI 可以判分。
- 当前实现：没有。“更多工具”里的复习按资料生成回忆题（`tools/service.py:198`），与课堂标记无关。 【2026-09-28 8-MF01，已合入】出题组件增加最终检验用途（每题带角度：复述/应用/辨析/找错/迁移，同一点不重复已用角度）；新增归因画像组件 course/check_agent.py（按错题归纳 ≤8 类问题、每类有证据、给老师的画像）。真实模型抽查：同一知识点五个角度各一题，归因能回指错题证据。检验阶段的编排与界面尚未做（架构师）。

- 解决：①改用 Keycloak 容器内的 kcadm 直接修改策略并备份原值，部署时用只过滤掉 realm 步骤的包装脚本（其余顺序、健康等待、自动回滚仍是部署包代码）；②接受标签或已确认的镜像 ID（另一处检查仍要求运行容器与标签都解析到该 ID）；③比较前把 Compose 输出的 $$ 还原；④忽略目录条目与只含 Manifest-Version/Created-By 的清单，其余（不许删类、只许新增 RegistrationCodes、SPI 不变）不放松。②③④ 各补了测试，部署包测试 12 项通过；每次修改都重算清单哈希后重新上传，旧包改名留存。
- 验证：prepare 通过（线上 jar 哈希一致；新增只有 RegistrationCodes 两类，改动只有 EmailCodeReset 与 NativeIdentityVerifier$Resource，三个 SPI 文件一字不差），build、deploy 通过，上线检查见 BUG-11。
- 规则：部署包要支持“按镜像 ID 引用”“Compose 转义”“不同打包工具”这些真实形态；管理接口相关步骤不能假设有对外 HTTPS 与长效令牌。

### [BUG-18] 课堂老师讲解偶有概念混淆

### [BUG-19] 课堂老师在不该出题的步骤自己追加随口问
- 状态：已解决（2026-09-28）
- 现象（真实模型课堂测试）：学习者插话或要求“别检验了”时，导演提示写了“不要出新题”，老师仍然在结尾用随口问标记把原题再问一遍，页面出现重复的题卡；如果老师换了措辞，待回答的题和屏幕上的题就对不上。
- 原因：老师 agent 只要输出了随口问标记就被当成一道新题显示，宿主没区分“这一步需不需要题”。
- 解决：宿主调用老师时标明这一步是否需要随口问：需要的（讲新点、答错后再确认、插话后回到原题）显示为题卡，并把待回答的题更新为屏幕上的这一题；不需要的步骤里老师自己加的问题并入讲解文字，不另起题卡。
- 验证：离线课堂测试 5 项通过；真实模型重跑时插话、改规则两步都没有再出现重复题卡。
- 规则：凡是会被宿主当作状态的 agent 输出（题目、判定），宿主都要按当前步骤决定是否采纳，不能“有就用”。
- 关联：[ARCH-07] [TEACH-06]
- 更新：2026-09-28

### [BUG-20] DeepSeek 工作日白天的调用不计价；正式生成的花费预估一直是空的
- 状态：部分解决（预估已修；工作日白天计价待 9-MF02）
- 现象（8-MF04 报告、架构师复查）：用量页和测试里 DeepSeek 调用全部显示“未定价”；正式生成前的花费预估金额一直为空，只显示 token。
- 原因：①DeepSeek 分高峰/闲时两档价，价格表的中国法定节假日日历是空的（holiday_calendar: null），计价代码为了不猜节假日，工作日 9–12、14–18 点的调用一律不计价（周末和其他时段能算出来）；②新建计划的花费预估调用价格表时没带“地区/服务档位”，永远匹配不到价格行。员工报告里归因为“缺推理 token 字段”，架构师用真实价格表逐步排查后确认不是。
- 排查：取一次真实课堂调用的用量，用线上下发的价格表（33 行）单独计价，逐项检查候选价格行：_period 返回 None → 高峰/闲时两行都被排除。
- 解决：②已修（2026-09-28）：网关提供 estimate_context()，预估与实际调用用同一套地区/档位。①派 9-MF02：按国务院办公厅官方通知录入节假日日历（带来源），日历覆盖不到的日期按高峰价给出“估算上限”并在界面标明，而不是空着。
- 验证：②全量测试通过；①待 9-MF02。
- 规则：费用相关的“算不出来”必须能在界面上看出原因；员工对原因的解释要用真实数据复核。
