1. 收据写好了，柜台却说没办完：中断恢复与幂等｜常被问

已落库的事实不能因为界面没保存，就被再办一次。这种“重试后仍只记一次”的效果叫幂等。[B01][B02] 一句话层。

处境（S）：模块检测最后一题已经在数据库里结算，课堂状态却要等老师总结完才保存；中途关闭后，重开还停在“检测中”，再结算会报 ATTEMPT_ALREADY_CLOSED，课程卡住。[B01] 任务（T）：让中断后的课堂接着走，并且不多记一次成绩和时长。行动（A）：操作前对照数据库，发现检测已经结束就补完收尾；结束检测、判定和记账都要能安全重试。[B01][B02] 三句话层。

另一个故障把同一条缝照得更清楚：判定已入库、老师回复失败，重答后判定从 1 条变成 2 条。修法是给每道待答题一个固定编号，再次处理沿用原判定；保存失败也必须报错，不能假装成功。[B02] 结果（R）：回归测试构造“数据库已结束、状态未保存”，恢复后记账与正常完成一致；判定重试和课堂保存失败也有独立测试。[B01][B02] 深一层。

资料室比喻：借书收据已经打印，柜台屏幕还没跳到“完成”，这时断电了。重开应先查收据，再补画面，而不是重新收一笔钱。边界是：这里不是把所有存储都放进同一个大事务，而是靠持久事实、固定编号和恢复逻辑，处理两次保存之间的缝隙。[B01][B02]

学到的工程判断：先明确哪份记录是事实，再决定怎样恢复；“再试一次”之前先问这一步是否已经落库。[B01][B02]

你可以这样跟面试官说（约一分钟以内）：我们遇到过检测最后一题答完后重开永久卡住。数据库已经结算，课堂状态还在检测中，重试就重复结束同一次检测。我参与核对时把这个中断窗口单独拿出来：先查是否已结束，再补收尾；判定用固定编号认出重试。测试特意停在两次保存之间，确认恢复后只结算一次。[B01][B02]

追问一：为什么不直接吞掉“已结束”错误？ 答：只吞错误没有补齐课堂收尾和记账；修法是识别已完成的事实，再走可重复的收尾路径。[B01]

追问二：有防多开锁，为什么还会中断？ 答：锁能限制同时写入，不能防止窗口关闭、断电或崩溃发生在两次保存之间。[B01]

中断恢复为什么要先查已经落库的事实？

  • 已落库的事实不能因为界面没保存，就被再办一次。[B01][B02]
  • 操作前对照数据库，发现检测已经结束就补完收尾。[B01][B02]
  • 给每道待答题一个固定编号，再次处理沿用原判定。[B01][B02]
  • 保存失败也必须报错，不能假装成功。[B01][B02]

2. 两家分馆改同一本账：离线修改不能被同步抹掉｜常被问

同步不能只看远端版本新不新，还得看本机有没有未上传的修改。[B03] 一句话层。

处境（S）：本机离线改了计划名或日期，同步后被另一台设备的版本覆盖，“待上传”从 1 条变成 0 条。任务（T）：保住本机修改，又能接纳远端改动。行动（A）：把整条覆盖改成逐字段合并：本机没改的字段用远端，两边都改的字段按修改时间选后一次，并提示冲突。[B03] 三句话层。

定位不是看页面感觉：用两个本地课程存储对象（CourseStore）构造本机待上传、远端更新的组合，直接看标题和待上传队列。实现用设备本地 UTC 纳秒与设备编号排序；时间相同按设备编号决胜。这里记录的是设备本地的高精度时间戳，采用 UTC 表示不代表设备的钟已经同步，设备的钟仍可能不准。[B03][B04] 结果（R）：不同字段并发修改、同字段后改保留与冲突提示都有离线回归；两台设备时钟差很多时，这个顺序可能不符合实际先后，真实双设备验证当时尚未完成。[B03] 深一层。

资料室比喻：甲分馆改书名，乙分馆改借阅日期，不该用乙的整页账把甲的书名擦掉；要对着格子合。比喻边界：两台设备没有一只共同的钟，本地时间不是绝对真相。这套规则是项目记录的冲突策略，不能说成解决了所有分布式一致性问题。[B03]

学到的工程判断：合并不仅决定值，还决定哪些修改仍待上传；提示用户发生过冲突，比悄悄覆盖更容易核对。[B03]

你可以这样跟面试官说（约一分钟以内）：我们查到离线修改被同步覆盖，连待上传标记都清掉了。根因是只按服务器版本覆盖整条记录。修成逐字段比较：不同字段各保留，同字段按本地时间和设备编号排序，提示用户。测试用两份独立 Store 互相同步，验证值和队列都没丢；我也会明确说，设备时钟偏差是这个方案的边界。[B03][B04]

追问一：这是服务器“最后写入赢”吗？ 答：这里比较的是字段的本地修改时间和设备编号，不是请求到服务器的到达顺序。[B03][B04]

追问二：只验证最终标题够吗？ 答：不够，还要验证本机没上传的修改没有丢、待上传标记没有被错误清掉。[B03]

逐字段合并保住了什么，还有什么边界？

  • 本机没改的字段用远端，两边都改的字段按修改时间选后一次，并提示冲突。[B03][B04]
  • 实现用设备本地 UTC 纳秒与设备编号排序；时间相同按设备编号决胜。[B03][B04]
  • 两台设备时钟差很多时，这个顺序可能不符合实际先后。[B03][B04]
  • 合并不仅决定值，还决定哪些修改仍待上传。[B03][B04]

3. 维修员是会员，却没有房门钥匙：迁移权限与发布失败｜常被问

迁移在开发机成功，不等于用线上那套角色权限也能成功。[B05] 一句话层。

处境（S）：上线 RAG（检索增强生成，先查资料再组织回答）功能时，负责升级数据库的迁移角色在 account_closure 模式中替换函数被拒；两步迁移整体回滚，库仍停在 0043，新表没有建成。上线脚本取管道输出却没检查退出码，仍继续部署 Java，服务健康也不能让不存在的表变出来。[B05] 任务（T）：按真实权限复现，修到迁移能成功而不扩大授权。行动（A）：本机照线上搭 PostgreSQL 角色，连“不继承成员权限”也照搬，重现 42501 权限错误。[B05] 三句话层。

关键是“成员”不等于“当前自动拥有权限”：迁移角色能切换到函数属主角色，但不自动继承它的 CREATE 权限，也就是创建数据库对象的权限。修复在替换函数前 SET LOCAL ROLE，结束后 RESET ROLE，不新增角色权限；上线脚本每步检查退出码，失败就停。[B05][B06] 结果（R）：本机从 0043 升到最新版、降回再重升（0043→head→0043→head）通过，注销清理只影响目标账号；线上重跑迁移退出码 0，三张 RAG 表启用并强制按行限制数据访问的 RLS，14 个清理函数属主没变，3253 条同步记录前后不变。[B05] 深一层。

资料室比喻：维修员属于管理团队，不代表他平时就拿着档案室钥匙；这项维修要按允许的方式临时换成持钥匙的身份，做完交回。边界是：身份切换由已有授权允许，并非冒充或跳过权限；健康检查成功也不等于每张业务表和每条业务路径都验收过。[B05][B06]

学到的工程判断：测试要断言“不该拥有的权限确实没有”，否则过宽的夹具会把生产故障藏起来。[B05]

你可以这样跟面试官说（约一分钟以内）：我们上线迁移时遇到权限不足，本地测试却通过。排查发现本地角色默认继承权限，线上不继承。于是按线上角色重搭数据库，复现后用已有的临时角色切换修函数，不去扩大授权。往返迁移、账号清理和线上只读核对都做了；同时补了脚本退出码检查，避免数据库没升级，应用却继续上线。[B05][B06]

追问一：为什么不直接给迁移角色 CREATE？ 答：已有可切换的函数属主角色，修复沿用这条路径，保留原有权限边界。[B05]

追问二：部署后健康接口 200 为什么仍有故障？ 答：那次 Java 正常运行，但 RAG 所需的表没建成；还要核迁移版本、表和业务权限。[B05]

怎样防止迁移测试比线上权限更宽？

  • 本机照线上搭 PostgreSQL 角色，连“不继承成员权限”也照搬。[B05][B06]
  • 修复在替换函数前 SET LOCAL ROLE，结束后 RESET ROLE，不新增角色权限。[B05][B06]
  • 上线脚本每步检查退出码，失败就停。[B05][B06]
  • 测试要断言“不该拥有的权限确实没有”。[B05][B06]

4. 抽屉刚打开就自己关：前端副作用竞态｜常被问

偶发测试失败可能是产品竞态，不能先把等待时间调大。[B11] 一句话层。

处境（S）：刚进入课堂或切小要点，快速点资料导航，浮层一闪就没了；同一测试修前 11 次失败 4 次。任务（T）：第一下点击就有效，同时切换内容时仍关闭旧浮层。行动（A）：排除未经证实的“墙钟影响”，追到普通 useEffect 晚执行——它在这里负责切换内容后的浮层清理：点击先开浮层，约 0.3 毫秒后旧清理动作把它关了。[B11] 三句话层。

修复换成 useLayoutEffect，让这次清理在新工具条能接到点击前完成，不延长等待、不删断言。[B11][B12] 结果（R）：新增确定性首次点击回归，修前失败修后通过；原测试连续 5/5，模拟上午、晚上、跨零点 3/3，目录复跑 8 项通过。记录仍标明用户亲测未做。[B11] 深一层。

资料室比喻：店员已把新抽屉交给读者，另一位店员才来执行“关旧抽屉”，结果把刚开的也关了。应在交出去之前完成整理。边界是：这里仅调整这一个同步清理的时机；不能把所有副作用都塞进布局阶段，否则会把更多工作压到显示前。[B11][B12]

学到的工程判断：先记录先后顺序，找到会交错的动作，再修时机；日期模拟用来排除猜想，不能把猜想当根因。[B11]

你可以这样跟面试官说（约一分钟以内）：资料导航的首次点击偶发失效，开始看着像测试不稳。追踪发现点击开浮层后，切小要点的 effect 才运行，把新浮层关了。改用布局阶段的清理，让工具条接收点击前状态已整理好。我们加确定性回归，不靠加等待；重复跑和跨时段模拟都通过，真人体验另行确认。[B11][B12]

追问一：为什么不是把测试多等一秒？ 答：浮层被关了，等再久也不会自己重新打开；要改交错顺序。[B11]

追问二：useLayoutEffect 可以到处代替 useEffect 吗？ 答：本例只放必须在可交互前完成的短清理，不能由一次成功推成通用替换规则。[B11][B12]

怎样证明首次点击失败是产品竞态？

  • 点击先开浮层，约 0.3 毫秒后旧清理动作把它关了。[B11][B12]
  • 修复换成 useLayoutEffect，让这次清理在新工具条能接到点击前完成。[B11][B12]
  • 不延长等待、不删断言。[B11][B12]
  • 新增确定性首次点击回归，修前失败修后通过。[B11][B12]

5. 草稿很多，正文为空：模型响应分层｜常被问

HTTP 成功、事件流结束和用户拿到正文，是三件不同的事。[B13] 一句话层。

处境（S）：课堂显示“软件出了点问题”，但 HTTP 200 表示请求成功，逐段传回的事件流也完整，以 end_turn 结束标记收尾，却只收到 thinking 思考内容块，没有正文；当天记录了两次这种空回复。任务（T）：对这个特定的空结果恢复一次，不能把所有错误都偷偷再发。行动（A）：把网络、流协议、正文分开看，确认还没上屏任何字时，静默再要一次；第二次仍空才提示，其他错误不走这条重试。[B13] 三句话层。

调用通过 gateway.defer_errors 暂缓首个错误的界面通知，日志保留 TEACHER_EMPTY_RETRY；这不是把失败从记录中抹掉。[B13][B14] 结果（R）：空一次后成功、连续两次空仍报错、其他错误不重试，现场与预取两种路径都有回归；相关 82 项通过，随 2.0.19 发布，记录仍为待用户亲测。[B13] 深一层。

资料室比喻：答题员收到题并打完草稿，却交了一张没有正文的答卷；快递签收只证明信封送到，不证明里面有答案。边界是：thinking 是接口返回的内容类型，不代表模型真实的内在思维，也不能拿这种日志保证最终内容正确；本次只修空正文的恢复。[B13]

学到的工程判断：重试条件要窄，且有次数边界；已经显示内容时不能照搬“无感重试”，否则读者会看到答案被换掉。[B13]

你可以这样跟面试官说（约一分钟以内）：我们查过一次模型接口成功却没正文的错误。HTTP 和流结束都正常，只有思考块。修法只针对“还没显示字、只有思考没有正文”：静默重试一次，仍空就报错，其他故障照旧。现场和预取都测了，日志保留第一次失败；这解决空回复恢复，不宣称解决模型正确率。[B13][B14]

追问一：为什么 HTTP 200 不能算业务成功？ 答：它没有证明响应包含课堂需要的正文，业务层还得检查内容。[B13]

追问二：重试会不会重复显示？ 答：这条重试只在还没显示任何字时触发，次数只限一次。[B13]

为什么模型调用要区分协议成功与正文成功？

  • HTTP 成功、事件流结束和用户拿到正文，是三件不同的事。[B13][B14]
  • 确认还没上屏任何字时，静默再要一次。[B13][B14]
  • 第二次仍空才提示，其他错误不走这条重试。[B13][B14]
  • 本次只修空正文的恢复。[B13][B14]

6. 门挡住了，搬家师傅一直等：真实更新不能只测替身｜常被问

跨进程更新要用真程序走通，不能只证明“假 App 会退出”。下文的真包就指实际打包的 Windows 应用。[B07] 一句话层。

处境（S）：更新下载完成，进度停在 100%，约 45 秒后报“App 没关闭，未替换”，用户三次尝试仍留在旧版。任务（T）：旧进程保存退出后才能换文件，失败又不能把已下载版本弄丢。行动（A）：沿日志查到更新器向主窗口发关闭消息，模态更新框却挡在上面；用桌面窗口框架 Qt 做最小实验证明关闭消息收不到。[B07] 三句话层。

修复不再依赖外部强行关窗：更新器确认进程窗口并写“已接手”回执，App 收到后自行保存退出，更新器等进程结束才替换。退不掉就保留下载，转成下次启动安装；同时修了 App 和启动器缓存根目录不同导致的回退路径失败，并写日志。[B07] 结果（R）：真包登录入口回执后 0.21 秒退出，主界面入口 0.192 秒退出；保存卡住 33 秒的场景走了下次启动安装，新版设置和 Key 保留。自动化没有证明新窗口一定抢到前台，这项仍要真人核对。[B07] 深一层。

资料室比喻：搬家师傅在门外喊“请关门”，里面却挂着一块挡门告示。正确交班是师傅签收工单，店员自己收好账本、关门，再让师傅换门。边界是：实际有进程身份确认、锁、签名和逐文件校验，回执不等于下载文件天然可信。[B07]

学到的工程判断：测试替身可以验证分支，但窗口消息、进程退出和跨版本路径必须再用真打包程序验。[B07]

你可以这样跟面试官说（约一分钟以内）：一次更新一直等旧进程退出，根因是模态框挡住了关闭消息。我们用最小窗口实验确认后改成交接协议：更新器签收，App 自己保存退出，再换文件。保存失败则保留下载转下次启动安装。最后用真包从两个入口更新，并验证设置、Key 和健康状态；替身测试通过不再当端到端通过。[B07]

追问一：为什么不直接杀进程？ 答：这次选择让 App 保存后自己退出；保存卡住时保留旧软件与下载，走下次启动安装。[B07]

追问二：只看新版窗口出现够吗？ 答：还核对健康状态、设置和 Key、pending 清理，以及 Updater 是否换成新版。[B07]

更新交班怎样兼顾退出与失败回退？

  • 更新器确认进程窗口并写“已接手”回执，App 收到后自行保存退出，更新器等进程结束才替换。[B07]
  • 退不掉就保留下载，转成下次启动安装。[B07]
  • 测试替身可以验证分支，但窗口消息、进程退出和跨版本路径必须再用真打包程序验。[B07]

学到的工程判断：清理正确性至少有两面——垃圾确实减少，业务文件逐字节不变；一次锁忙不是永久放弃的理由。[B08]

追问一：为什么拿锁？ 答：避免把下载或安装正在使用的暂存目录当垃圾删掉。[B08]

追问二：怎样证明没删错？ 答：除了看占用下降，还逐字节核对学习文件，并验证待装版本保护。[B08]

  • 清理前拿下载锁和安装锁，锁忙就延后。[B08]
  • 保护待装版本，遇到含用户数据目录 Data 的目录不删除。[B08]

8. 店面换新，维修工具却没换：更新器的交班竞态｜偶尔问

资料室比喻：新店开门了，维修师傅却还拿着旧工具箱；下次修门仍会用旧办法。边界是：这是两个可执行组件与锁的接续，不是多点几次按钮；重试只针对忙锁和未结束事务，不承诺所有失败都会重试成功。[B09][B10]

学到的工程判断：完成标准要覆盖后续维护链，不只检查眼前窗口；“暂缓”要有明确终态和可追踪记录。[B09]

追问一：为什么不能无限重试？ 答：实现用了明确的有限等待序列，耗尽后保留最终 DEFERRED，让后续启动有状态可查。[B09][B10]

追问二：真包第一次成功说明重试可靠了吗？ 答：只说明正常接续成功；忙锁重试靠专门的离线场景覆盖。[B09]

Updater 交班为什么需要独立验收？

9. 维修场地被别人占了：测试夹具污染全进程｜偶尔问

测试辅助代码在导入时改全局环境，也能制造真实故障。[B15] 一句话层。

处境（S）：一场全量测试约跑到 74% 才发现文件写进共享目录；当时共享目录约 618 MB，多场还会共用构建目录。任务（T）：共享可复用的编译缓存，隔离每场临时文件。行动（A）：查到 pytest 的共享测试配置文件 conftest 在导入时改 TEMP、TMP、TMPDIR 等临时目录环境变量；pytest 只是收集到该目录，就改了整场进程的环境。[B15] 三句话层。

10. 送书车还在路上，先把订单扔了：网络超时与降级｜偶尔问

还在持续下载的用户资料，不应被一个整页总时限扔掉。[B17] 一句话层。

处境（S）：小林 coding 专题目录 42 页只读到 18 页，20 页撞到 15 秒资料总时限，4 页 SSL 连接断开；普通网址还会因 robots.txt 一时读不到而失败——它是网站声明自动抓取规则的文件，不是登录或授权凭据。任务（T）：让用户选的页读完，临时断连能恢复，整本识别失败不破坏单页读取。行动（A）：把页失败清单与总时限截止点对照，拆开整页总时长与网络长时间无数据的超时，并给临时失败加重试。[B17] 三句话层。

用户自选资料去掉总时限，保留连接和无字节超时；临时错误共尝试 3 次，等待 1、2 秒，有 Retry-After 就遵循它，整批后补读失败页一轮。Retry-After 是服务器给出的建议等待时间。robots 重试仍不可用就不多页抓取，退回用户给的单页并说明；取消仍有效。[B17][B18] 结果（R）：30 秒慢下载等 20 项测试覆盖，真实专题读到 42/42、320176 字，13 次网络失败靠恢复补回，约用 26 分钟；这次没有跑后续资料结构模型步骤。[B17] 深一层。

资料室比喻：送书车仍在一箱箱卸货，不能因为整车超过 15 秒就把订单扔掉；但司机长时间没有消息，要能识别卡住并重试。边界是：没有总时限不等于没有网络超时，也不等于可无限抓站；整站仍按目录、robots 和用户选择处理。[B17][B18]

学到的工程判断：新增整本能力失败时，保留原来单页可用的路；统计最终成功页，也保留每页失败原因和实际用时。[B17]

你可以这样跟面试官说（约一分钟以内）：网页书只读到 18/42 页，失败清单显示多数是整页 15 秒时限，不是正文不可读。用户自选资料改成等待持续下载，只保留网络超时、有限重试和取消；robots 暂时读不到时不抓整本，但仍尝试用户给的单页。复测读到 42/42，花了约 26 分钟；我不会拿它冒充后续建计划也完成。[B17][B18]

追问一：不设总时限会不会一直卡住？ 答：连接和长时间收不到字节仍会超时，用户也能取消；取消总时限不是取消所有退出条件。[B17]

追问二：为什么推荐筛选仍有时限？ 答：这次修复只覆盖用户自选资料；AI 筛候选链接的 15 秒等时限没有改，不能混成同一条路径。[B17]

网络慢、临时失败和整本识别失败怎样分别处理？

  • 用户自选资料去掉总时限，保留连接和无字节超时。[B17][B18]
  • 临时错误共尝试 3 次，等待 1、2 秒，有 Retry-After 就遵循它。[B17][B18]
  • 整批后补读失败页一轮。[B17][B18]
  • robots 重试仍不可用就不多页抓取，退回用户给的单页并说明。[B17][B18]
