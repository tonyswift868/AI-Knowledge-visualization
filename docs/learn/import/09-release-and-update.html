09 发布与软件内更新

事实基线：7df4f6ea。[D01]

本篇标“偶尔问”表示学习优先级判断，不是面试频率统计；按每节的一句话层、三句话层和深一层来学。[D01]

贯穿场景：把发版想成出版社把新书送到分馆——构建像排版，签名像出版社盖章，更新服务器像分发站，客户端先看通知再验收新书。这个比喻只帮助记流程：软件不是纸书，签名只能证明清单由受信密钥签出且内容未被改动，不能证明软件没有缺陷。[P03,U02]

1. 从代码到待签名软件包｜偶尔问

构建和签名分开，让生成软件包的机器不必持有正式私钥，清单再交给本机签名步骤核对和签出。[P01,P03] 一句话层。

架构师在 GitHub 手动运行页选代码分支或标签，填写版本号和说明，再触发构建工作流 mf-build。[P01] GitHub Actions 的 Windows 构建机器把程序和依赖整理成可运行目录，并产出未签名清单。[P01] 正式发布的构建会把服务器缺少的文件对象送到暂存区；只构建、不发布的模式则不上传。[P01,P02] 三句话层。

构建清单列出文件路径、大小、SHA-256 和源代码提交号。[P02] 流水线要求清单里的源代码提交号等于指定基线。[P02] 正式打包前还检查源码目录干净、当前提交就是所选基线；提交号本身不是从二进制还原源码的证明。[P02] SHA-256 是文件指纹，供核对文件内容；它不是出版社身份凭证，身份要靠数字签名验证。[P03] 正式发版前先在本机做产品验证，再审阅合并；版本号一经发布，不把同一个版本号改成另一套内容。[P04] 深一层。

想象编辑先把书排好版、列出每个文件的目录和指纹，再把待审样书交出去。这个场景说明构建与签名是两步；它不表示 GitHub runner 持有正式签名私钥。[P01,P03]

你可以这样跟面试官说：“我把构建和发布拆成可核对的步骤：先在确定的代码提交上生成软件包和文件清单，验证清单确实来自这次基线，再把待签名产物交给发布流程。这样一旦版本和源码对不上，流程会在上线前停下来。”[P01,P02]

代码怎样成为待签名的软件包？

  • 架构师在 GitHub 手动运行页选代码分支或标签，填写版本号和说明，再触发构建工作流 mf-build。[P01]
  • GitHub Actions 的 Windows 构建机器把程序和依赖整理成可运行目录，并产出未签名清单。[P01]
  • 流水线要求清单里的源代码提交号等于指定基线。[P02]

2. 本机盖章，服务器发布｜偶尔问

正式签名私钥留在架构师本机，服务器只收到已签名清单。[P03] 签名不是加密。[P03] 一句话层。

架构师在本机核对签名密钥身份并签出清单，再把签好的 stable.json 放进服务器暂存区。[P03] 发布工作流 mf-publish 先验签和检查版本规则，再核对文件对象、归档该版清单。[P04] 线上清单和小指针各自原子替换：读者看到的是各文件完整的旧内容或新内容，但两份文件不是一起完成的一个原子事务。[P04,U01] 三句话层。

客户端用随包受信公钥验证签名清单，确认清单的来源和完整性。[U02] latest.json 是供客户端判断清单是否变化的小指针。[U01] 指针与清单不一致时，客户端采用已经验签的 stable.json。[U01] 服务器按文件的内容指纹为文件命名，存在 objects 目录，内容相同就不必重复传。[P04] 日常发布默认不编安装程序，下载站继续提供上一次已编译的安装包，新用户装好后通过软件内更新跟上新版。[P04] 若清单已切换、随后安装程序编译失败，不能把部分成功说成整条发布完成。[P04] 深一层。

这像出版社先盖章，再把新书放进分馆目录；通知卡片可以帮分馆决定要不要取完整目录，但不能代替印章。比喻不成立的地方是：服务器发布有两个原子文件替换步骤，指针与清单可能短暂不同，客户端必须以通过签名验证的清单为准。[P04,U01]

你可以这样跟面试官说：“签名私钥只在本机使用，服务器收到的是签好的清单和按内容存放的文件。发布端先检查版本规则与文件指纹，再切换线上清单；客户端看到的小指针只负责提醒它是否需要取完整清单，不能替清单授权更新。”[P03,P04,U01]

签名清单与小指针各负责什么？

  • 客户端用随包受信公钥验证签名清单，确认清单的来源和完整性。[U02]
  • latest.json 是供客户端判断清单是否变化的小指针。[U01]
  • 指针与清单不一致时，客户端采用已经验签的 stable.json。[U01]

3. 客户端检查版本与登录门控｜偶尔问

客户端先看一张小指针，真正的更新决定来自通过验签的完整清单。[U01,U02] 一句话层。

客户端先取 latest.json，把版本号、metadata 版本、清单 SHA-256 和大小与本机已验签的清单比较；一致时重新核对缓存清单的有效期和策略，就不必下载完整清单。[U01] 指针变化、缺失或不合法时，客户端取 stable.json 并验证 Ed25519 签名；如果指针与清单不一致，记录差异但以签名清单继续判断。[U01,U02] 签名清单还要通过产品身份、版本顺序、渠道、有效期、本机已见过的最高元数据版本（高水位）和强制更新线等检查。[U02] 三句话层。

用户可以填写登录表单，提交请求会等本轮更新检查。[U03] 检查失败或等到 15 秒上限时，只按本机已验签的策略决定是否放行。[U03] 若没有可用的已验证状态，客户端要求修复，不凭空放行。[U03] 如果缓存记着强制更新，断网不会把强制要求降成可选；非强制更新可稍后处理，强制更新没有“稍后”。[U03] 已登录后才发现必须更新，也会阻止继续操作；课堂先保存进度和未发送输入，再弹更新框，保存失败就提示重试。[U09] 可选更新仍不在课堂打扰。[U09] 公开下载先走域名，连接或验证失败时尝试固定 IP 备用源，两条路径都要验签。[U10] 当前基线仍把登录更新框被截（BUG-110）和后台预下载撞锁后显示错误（BUG-111）列为待修。[U04] 深一层。

这像读者先看书店的到货牌：牌子没变，就不用再搬整本目录；牌子变了，才取目录核对出版社印章。它不表示指针本身可信，也不表示离线时一定可以继续使用——本机若没有有效的已验证策略，登录会被挡住。[U01,U03]

你可以这样跟面试官说：“客户端先看本机是否有一份仍有效、已经验签的版本策略，再按小指针判断是否需要取完整清单。指针只是提示，真正决定版本的是验签后的清单；断网时也不会把强制更新变成可选。如果本机没有可用的已验证状态，客户端会要求修复，而不是猜一个版本放行。”[U01,U02,U03]

离线时，客户端依据什么放行？

  • 检查失败或等到 15 秒上限时，只按本机已验签的策略决定是否放行。[U03]
  • 若没有可用的已验证状态，客户端要求修复，不凭空放行。[U03]
  • 如果缓存记着强制更新，断网不会把强制要求降成可选；非强制更新可稍后处理，强制更新没有“稍后”。[U03]

4. 更新交接、文件替换与恢复｜偶尔问

更新器先核对下载内容，再交给安装事务；新程序健康可见后才算更新成功。[U05,U07] 一句话层。

客户端重新验签并比对文件指纹，内容相同的本机文件复用，只下载缺少或不同的文件，再准备完整暂存版本。[U05,U06] 点更新后，App 把请求交给独立的更新协调进程，收到接手回执后保存必要状态并自行退出。[U07] 安装事务核对目标文件、保留旧版、换入新 App，确认新窗口可见并响应后才写成健康状态 HEALTHY。[U07] 三句话层。

下载前客户端重新验签，并逐项比对本机 App 文件与目标清单的大小和 SHA-256。[U05] 安装事务把暂存目录移入 staging，核对签名清单和文件。[U07] 新程序必须报告版本正确且窗口可见、可响应，事务才写成 HEALTHY。[U07] 这份“健康证明”只确认目标进程和窗口，不代表所有学习功能都已测完。[U07] 后台会尽量提前准备暂存，但当前基线仍有预下载撞锁失败的问题，点击后不能假定一定已准备好。[U06,U04] 已有旧版且切换后失败时，事务尝试恢复旧版并重新确认健康；初装没有上一版，恢复检查失败也要进入失败或修复路径。[U07] 等 App 退出超时而暂存仍有效时，保留待装状态，下次从启动器再试。[U07] 新版启动会刷新 Updater，锁忙时有限重试；后台清理过期程序副本，保护当前待装版本，学习 Data 不动。[U08] 程序副本清理不等于清空所有对象缓存。[U08] 深一层。

像分馆在闭馆后换书架：先把经过核对的新书移进待摆区，逐本核对齐了再切换书架；新书打开确认正常，旧书留在旁边以便回退。这个比喻不代表每个缓存文件都会被清除，也不表示“下载完成”就等于“更新成功”。[U07,U08]

你可以这样跟面试官说：“更新是有回退点的文件事务：先准备并校验目标文件，交接后 App 自己退出，再换目录并确认新窗口可用。失败时尝试恢复旧版，还要确认旧版能启动；如果退出超时，下载可以留到下次启动再装。程序副本会清理，学习数据不动。”[U05,U07,U08]

为什么更新不能只看下载进度到 100%？

  • 下载前客户端重新验签，并逐项比对本机 App 文件与目标清单的大小和 SHA-256。[U05]
  • 安装事务把暂存目录移入 staging，核对签名清单和文件。[U07]
  • 新程序必须报告版本正确且窗口可见、可响应，事务才写成 HEALTHY。[U07]

5. 真打包排练与故障证据｜偶尔问

单元测试能检查函数，真打包排练才能检查启动器、App、Updater 跨进程交接和安装目录切换是否真的接得上。[R01] 一句话层。

软件内更新曾出现下载到 100% 后仍失败：模态更新框挡住了发给登录窗或主界面的关闭消息，旧流程等不到 App 退出，随后回滚。[R01] 修复后，App 把任务交给 Updater 并收到接手回执，再保存状态、关闭窗口并自行退出；Updater 等 App 进程结束后换文件并重启。[R01,R02] 因而排练用真冻结包和测试签名，并从桌面启动器走更新；网页按钮用 CDP，原生安装与更新按钮用 UI Automation，不能只用替身关闭 App。[R01,R03] 三句话层。

发版规矩是先在本机验证并审阅，再让 GitHub 对一个确定版本执行一次发布；跨进程、跨版本的更新路径要用真打包程序验证。[P04,R01] 这只能证明本机排练覆盖到的路径，不等于所有用户环境都已实测。[R01] 深一层。

这像出版社先在本地把装订、交接和上架走一遍，再正式印发；纸面流程图能看出步骤，不能证明机器上的进程真的交接成功。比喻不成立的地方是，安装和更新还受 Windows 进程、文件锁及用户目录影响。[R01,R02]

你可以这样跟面试官说：“我会把更新当成跨进程的文件事务来验。测试会从桌面启动器打开真打包版本，实际点更新，确认旧进程退出、新版本换入、健康握手通过；替身测试能覆盖分支，但不能替代这条端到端证据。”[R01,R03]

为什么不能只用替身证明更新成功？

  • 软件内更新曾出现下载到 100% 后仍失败：模态更新框挡住了发给登录窗或主界面的关闭消息，旧流程等不到 App 退出，随后回滚。[R01]
  • 修复后，App 把任务交给 Updater 并收到接手回执，再保存状态、关闭窗口并自行退出；Updater 等 App 进程结束后换文件并重启。[R01,R02]
  • 因而排练用真冻结包和测试签名，并从桌面启动器走更新；网页按钮用 CDP，原生安装与更新按钮用 UI Automation，不能只用替身关闭 App。[R01,R03]
