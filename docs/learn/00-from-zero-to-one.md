# 从零到一：MentorFlow 是怎么一步步搭起来的

这条主线讲的是产品怎样长成今天的样子。它不是“一个人敲出了几万行代码”的故事：仓库历史能证明代码和功能何时出现，项目记录能证明哪些需求与取舍由用户确定。这份学习资料任务明确安排了架构师拆分、多名 GPT 员工协作和回执复核；旧的交付回执也留下了类似的分工实例。我们只把有证据的协作说成事实，不把它泛化成每个历史改动都由同一种方式完成。没有留下证据的早期动机，我们就不替它编理由。[H01]

可以把 MentorFlow 想成一间不断改造的自习室：先出现一套学习远征的底子，后来逐渐变成有资料、有计划、有老师的桌面学习软件；再把同步、安装、更新和服务器这些“水电门锁”补齐，最后才接入资料问答。读完这七站，你应能讲清它从哪里来、怎么工作、又怎样一点点变得可靠。

## 第一站：先有学习远征的实验底子

远征起步，逐步长成课堂。2026 年 7 月 13 日的最早提交已经出现“Learning Expedition（学习远征）”和证据驱动的学习基础。现在能确认的是：项目从这套学习实验起步；单凭提交记录，不能确定最初为什么选这个方向，也不能把后来产品的全部想法倒推成当时的计划。[H02]

可以把它想成自习室还没装修好，先搭了一张能跑流程的工作台。历史还提到“战斗回放”，这是早期远征实验中的功能名；它说明当时的项目形态带有实验性质，不代表今天的软件要做成游戏。到 7 月 23 日，历史里又出现排程、重排、知识转换、导师决策和学习地图等基础。这说明系统开始从单一实验长出“安排学习—处理知识—给反馈”的组成部分。[H03]

**你可以这样跟面试官说：**“仓库最早能追到 2026 年 7 月 13 日，先有学习远征相关实现。之后陆续出现排程、知识地图和导师流程。早期动机没有足够记录，我会把能证明的实现和自己的推测分开讲。”

## 第二站：把零散能力收成一个能陪人学习的产品

学习成课，老师开始陪学。到 8 月，项目历史出现本地学习地图、原生课堂、通用知识地图和教师自适应等实现。可以把它理解成自习室从工作台变成一间教室：不只排“今天学什么”，也开始关心知识如何组织、老师如何讲、学生怎样回应。这个比喻只说明功能逐渐连起来，不表示产品最初就有完整蓝图。[H04]

当前产品定位是 AI 教师平台：用户用资料建立计划，按天学习，在课堂中由老师讲解和反馈；系统还包含检测与报告。项目边界也逐渐明确：程序负责流程、数据和规则，模型提供文字或受约束的结构化结果，不能直接改学习状态。[H05]

**你可以这样跟面试官说：**“项目从学习流程实验逐步发展成桌面 AI 学习产品。它围绕资料建计划、每天上课和学习反馈组织功能；模型参与生成内容，程序掌握状态与规则。”

### 为什么不让 AI 直接改学习进度？

- 参考要点：AI 返回文字或受约束的结构化结果，程序校验后再处理。
- 参考要点：计划、规则、进度和账本由宿主状态机按用户操作改变。
- 参考要点：这样界面上的老师可以参与讲解，不能绕过程序规则自行记账。[H05]

## 第三站：2026 年 9 月 29 日，把旧底子换成清楚的结构

旧码退场，重新接好流程。项目不是一路往旧代码上加功能。9 月 29 日的记录明确标出“旧代码退场”，仓库当天也有桌面界面与新学习流程相关重构。之后仍能看到桥接接口、课堂恢复、计划写入与同步等衔接问题被逐项修复。像自习室重新布线：桌椅还在服务学习，但线路和房间分区换了，刚接上的设备也会暴露新的接触不良。[H08]

这次转向的重要经验是：重构不代表工作结束，旧数据、页面桥、课堂状态和服务器接口都必须重新接稳。项目记录保留了这些具体缺陷和关闭状态；我们可以说系统经历过重构与修复，不能仅凭代码历史声称所有变化都源自某个未记载的用户选择。[H09]

**你可以这样跟面试官说：**“9 月 29 日项目退场了旧代码并重整结构。之后修过桥接、课堂恢复、数据写入和同步问题。重构只是换骨架，真正完成还要把旧数据和各条流程接回去。”

## 第四站：重构后把课堂接稳，再给 AI 划出资料边界

有题才考，老师依原文教。看重构后逐步形成的分工，今天的软件外面是 Windows 桌面窗口，里面显示 React 学习界面；PySide6 和 Qt WebEngine 承载网页视图，页面通过桥接调用 Python 宿主。Python 客户端负责学习流程与模型调用，SQLite 保存本地学习数据。像教室里的白板连着老师的控制台：白板负责呈现和操作，背后的宿主负责真正的流程和记录。[H06]

实际建计划时，用户先说明目标和可用资料，系统整理计划结构；确认后再按资料原文目录切出知识点、小要点或资料导航，并生成学习地图。要留意发布边界：当前状态记录里，这套按目录切点的新结构已合入、但尚未随当时版本发布；不能把“已在代码里”说成每位用户都已在正式版用上。上课时，程序按计划推进讲解、互动和记录。比喻的边界是：界面不是一张“聪明白板”，它本身不决定学习进度；进度与账本由宿主和本地数据规则负责。[H07]

2026 年 10 月 3 日、6 日，方向有了一次重要转弯：最初让 AI 找资料、出题、判题，实测却不稳定、成本高，题和分数也不可信。用户因此定下新边界：题来自资料原题或用户上传；没有题就只学不考；老师按原文讲，可以举生活例子，但不能推出原文没有的结论。像自习室老师终于有了清楚的教学约定：可以解释讲义，不能临时编一份答案再自己判分。这是已记录的取舍，不是在说模型永远不能做这些事。[H17]

**你可以这样跟面试官说：**“桌面端用 PySide6 显示 React 界面，页面经桥接调用 Python。Python 管计划和课堂流程，本地 SQLite 保存学习数据。建计划先整理目标和资料。后来按实测收紧 AI 边界：题用资料原题，没题只学不考，老师围绕原文解释。”

## 第五站：让它能跨设备、能安装，也能在真软件上更新

本机记账，同步接续进度。学习记录要能留住，用户换设备也要接得上。客户端把本地变化放进待同步队列，再与服务器同步；冲突和重复请求要有规则，断线时也不能假装“什么都没有”。像自习室的借还登记和异地分馆：本地记录是手边账本，服务器帮同一账号在不同设备间接续。用户资料原件不随同步上传。[H10]

另一条链是把程序交给用户：构建、签名、发布、下载、验签、替换和恢复，各环都要在真实打包软件上排练。项目状态记录了安装覆盖和软件内更新的用户实测，也记录全新安装和真实注册仍有未验证项。正如装好门锁不等于每种进门方式都验过，不能把部分更新成功说成整条发布链已无风险。[H11]

**你可以这样跟面试官说：**“桌面端保留本地学习数据，再通过服务器同步账号数据；更新则走单独的签名与验签链。项目用真打包程序验证过覆盖安装和软件内更新，也会明确标出还没由用户走通的场景。”

### 哪些东西不会随账号同步？

- 参考要点：学习计划、进度、作答记录和报告等账号数据会同步。
- 参考要点：用户上传的原始文件、大型 Live2D 模型和朗读引擎不上传服务器。
- 参考要点：另一台设备没有原文件时，会提示原文件留在另一台设备。[H10]

## 第六站：把 AI 员工变成一支有边界的开发队伍

任务分工，回执核对结果。这个项目当前的开发制度也值得讲。在本批学习资料工作中，架构师把需求拆成有范围的任务文件，交给多个 GPT 员工并行处理；员工按任务范围完成工作并写回执，说明做了什么、依据是什么、怎样验证。架构师再负责对齐接口、审查证据和决定怎样集成。像总设计师把自习室装修拆成电路、桌椅和门禁几张工单：每个施工队有明确边界，回执让总设计师知道哪些已经接好。AI 生成代码不等于用户亲手逐行写代码，面试时应分别说清需求、取舍、组织实现、审查和验证各是谁做的。[H12]

开发里还有“真打包排练”：关键流程不能只在代码测试里看起来正常，还要在用户会拿到的安装包和更新器上走。现有记录也强调用户本人实测才算正式验收。把这些过程讲清楚，比说“我用 AI 写了整个软件”更准确，也更能回答协作和质量控制的问题。[H13]

**你可以这样跟面试官说：**“我借助 AI 架构师和多个 GPT 员工协作：需求和取舍由我确认，架构师拆任务、审查和安排集成，员工按范围实现并交回执。具体实现由 AI 完成的部分我会如实说明，重要流程还要用真打包程序排练并由用户验收。”

### 为什么还要用真打包软件排练旧版到新版更新？

- 参考要点：代码测试不能代替安装包和更新器的真实替换流程。
- 参考要点：要确认下载、验签、替换、失败恢复和已有计划保留等环节。
- 参考要点：更新相关功能需在真实打包程序走通后，再交用户本人验收。[H13]

## 第七站：服务器换成 Java，再让资料能被问到

后端迁移，检索交回原文。客户端仍以 Python 为中心；账号和同步等服务器业务后来逐块迁为 Java。项目记录写明，用户的求职方向是 Java + AI，因此服务器适合 Java 的业务部分按计划迁移；提示词和 AI 编排仍留在 Python，不为迁移而硬改。迁移时先用同一 HTTP 契约对照，再分块接入；2026 年 10 月 16 日，Java 后端正式上线，Python 服务停流量并保留回退。这里讲的是有证据的需求和工程步骤，不是说 Java 天然比 Python 好。[H14]

随后接入资料问答（RAG）：用户在本机选择资料，客户端抽取文字块，服务器为文字建立向量并检索相关原文，再把片段交回客户端；最终回答仍由客户端调用用户选择的模型生成。像自习室的资料室按问题找出几段可能相关的原文，交给老师组织解释；找到相似段落不等于它一定完整或正确，所以答案应连同引用核对。2026 年 10 月 17 日服务器端资料库准备好，客户端功能随 2.0.21 发布，项目状态仍将用户亲测列为下一步。[H15]

主线到这里收束：桌面端负责学习体验，Java 服务器负责账号、同步和检索，资料问答把“找原文”和“组织回答”拆成两步。下一步专题会逐层拆开技术栈、RAG、建计划、课堂、同步、账号、更新与故障故事。[H16]

**你可以这样跟面试官说：**“客户端还是 Python，服务器业务按用户的 Java + AI 求职方向逐块迁到 Java，并通过 HTTP 契约和分步切换控制风险。RAG 服务只检索资料片段，客户端再用用户的模型生成回答；检索不保证答案正确。”

### MentorFlow 为什么把检索和回答拆开？

- 参考要点：资料由客户端抽取文字，原文件不上传服务器。
- 参考要点：Java 服务负责片段检索，客户端负责调用用户选择的模型生成答案。
- 参考要点：检索片段只是证据候选，回答仍要看原文核对。

## 学习路线：带着这条主线继续学

把七站压成两句话：MentorFlow 从学习远征和排程实验起步，逐渐长成以资料计划和课堂为中心的桌面 AI 学习软件；9 月底重整旧代码并补齐流程衔接，之后建设同步、安装更新和真机验收链。

再往后，服务器账号和同步业务逐步迁到 Java，AI 提示词与编排仍在 Python，RAG 则把资料检索和回答组织拆成两步。开发中由架构师组织 AI 员工按任务协作，以回执和真实排练核对交付；每段职责都要按证据准确归属。

下一步先读 [02 技术栈](02-tech-stack.md)，认识每个房间的材料；再读 [04 RAG](04-rag-from-upload-to-answer.md)，跟一份资料走完“抽取—检索—回答”。之后按 README 的计划、课堂、同步、账号与更新专题补齐整条链。面试中不确定的早期动机就说明记录没有证明；没有亲自写的代码也不要说成亲手实现。
