# MentorFlow 主动式 AI 教学链真实实现审计

审计日期：2026-07-25  
审计分支：`recovery/session-replay-20260723`  
审计原则：以下“审计结论”描述本任务开始时的真实工作树；不依据页面文案或历史报告推断。工作区存在大量未提交修改，尤其涉及 `backend/app/main.py`、`db.py`、`orm.py`、`services.py`、`learning_run.py`、`frontend/src/App.tsx`。本任务不覆盖这些修改，不修改 KKS、Blender、角色卡或教师模型渲染代码。

## 2026-07-25 通用化复审

用户明确纠正：LeetCode 150 只是任意资料的测试样例，不是产品内置课程。复审后已撤销所有本轮 Hot150 专用模块、固定日期、题号和题目判题规则。当前新增实现以任意上传资料为输入：

- 文件内容决定知识点、解释、验收方式和完全掌握估时；
- 真实 Provider 可生成语义知识地图，但每个节点必须通过 chunk 来源校验；
- 未配置真实 Provider 时明确返回 `structural_fallback`，不冒充 AI；
- 相邻章节不再自动伪装成 prerequisite；
- 长资料的 Provider 分批结果会在落库前全局合并同名节点和来源，并过滤悬空、自环、重复与成环依赖；
- 完全掌握分钟拆为理解、回忆、引导练习、独立应用和复习；
- 计划使用用户任意起止日期、星期、不可用日、特殊日期和每日容量；
- 单击一次上传按钮会真实串行完成资料、默认回执、知识地图和计划四步，不需要预置课程指标；
- 教学检查直接使用资料生成的验收条件，不再把物理等资料硬套“复杂度/数组/代码”模板；
- 没有真实 Provider 或领域验证器时，自报“已理解”不会更新掌握度或完成分钟；
- 最终独立阶段通过后才创建持久化复习项，并可真实执行 +1、+3、+7 日复测；失败或提示依赖不会升级掌握；
- 只有上传资料同时提供已验证参考实现、样例/边界/隐藏测试和提示时才启用代码判题，普通资料不会被模型臆造为测试包；
- LeetCode、物理、数据库或其他资料都走同一 API 和数据模型。

当前复审实测支持 PDF、DOCX、Markdown/TXT/HTML、CSV/JSON/YAML/XML/RTF、多种代码文本，以及 PPTX/XLSX/EPUB 的文本层解析。图片/扫描 PDF OCR、音频、视频、复杂 Office 对象仍未验证，不能把“常见学习资料格式”夸大为“任何二进制文件”。

## 实施后逐项状态对照

1. **文件上传：可用。** 原始字节持久化，失败返回明确错误；失败材料再次上传仍返回失败，不会伪装为成功去重。
2. **格式：有明确白名单。** 支持 PDF、DOCX、Markdown/TXT/HTML、CSV/JSON/YAML/XML/RTF、常见源代码，以及 PPTX/XLSX/EPUB 的文本层；OCR、音视频未实现。
3. **原件与哈希：已实现。** 保存文件名、MIME、大小、SHA-256、上传时间、workspace 和存储路径；50 MiB 上限与压缩包展开预算已执行。
4. **正文解析：已实现。** 不是固定演示文本；结构化文本会做 JSON/YAML/XML/CSV 语法校验，重命名二进制文本会被拒绝。
5. **可追溯 chunk：已实现。** chunk 保存文件、页码、段落号、字符起止、序号、内容哈希和原文。
6. **检索：关键词检索可用，向量检索未实现。** 所有结果携带 chunk 证据并按 workspace 隔离。
7. **精确引用：已实现到资料能力边界。** 返回文件、页/段落、字符范围、原文 quote；没有页码的文本文件不会伪造页码。
8. **知识点：真实生成并持久化。** 含解释、难度、分项与总掌握分钟、验收方式、资料和来源证据。
9. **前置依赖：真实表结构可用。** `provider_grounded` 会生成并校验依赖；无 Provider 的结构降级不会猜测语义关系，因此可能为 0 条边。
10. **知识图谱：是真实数据库结构。** 节点与边均可查询、去重、合并、做悬空/自环/重复/循环拦截，不是静态画布。
11. **学习回执：已持久化。** 保存目标、基础、目标水平、起止日期、可学习星期、固定休息日、额外不可用日、特殊日期分钟、每日预算、偏好、备注、资料范围和是否允许调整建议。
12. **个性化计划：已实现。** 使用回执、知识点难度、分项估时、依赖和日历容量；没有预置题库目标。
13. **每日任务分钟：按任务装箱。** 先估每个知识点的理解/回忆/引导练习/独立应用/复习分钟，再按依赖和逐日容量排入；不是按题数或总字数平均。
14. **三类时间：已区分。** 每项任务分别保存 estimated/completed/actual elapsed minutes，实际分钟只接受显式、幂等的活动事件。
15. **主动教学：状态机可主动推进。** 能讲解、举例、检查、选择继续/补救/降低难度并保存下一动作；真实 DeepSeek 表达层尚未现场验证。
16. **补救教学：已实现。** “不懂/为什么”等会暂停主线，创建有标准分钟的补救任务并压入持久化栈。
17. **恢复路线：已实现。** 补救通过后回到保存的主线位置；补救任务参加同一计划重排，不会被当成免费时间。
18. **掌握度：由证据驱动。** 无验证器时自报理解不加分；代码需真实测试，复习需独立延迟复测。通用非代码领域仍受 Provider rubric/领域验证器能力限制。
19. **完整/部分边界：** 摄取、证据、结构图、容量计划、补救/恢复、持久化复习和受限 Python 判题已可运行；语义依赖、跨领域掌握证明、OCR/音视频和生产级代码沙箱仍为部分或未完成。
20. **最短可行路线已落地。** 通用 API、数据库、前端入口、测试资料、验收脚本和真实 Chromium E2E 已接通；下一阶段是增强语义抽取与更多领域验证器，而不是增加某个题库的硬编码。

以下二十项保留为任务开始时的历史审计快照；实施后的当前状态和验证边界以 `ACTIVE_TEACHING_CHAIN_IMPLEMENTATION_REPORT.md` 为准。

## 总结

任务开始时已有真实的上传解析、SQLite、BM25/关键词检索、引用校验、知识地图核心、计划、LearningRun 和掌握度事件骨架，但完整主动教学链没有接通。最严重的断点是：

- 原文件字节 SHA-256、大小与 chunk 字符位置未统一持久化；
- 当前知识地图 API 因工作树改动不可用，实测返回 405；
- 主计划仍只消费前 12 个 chunk，每天通常只安排一个 30–45 分钟任务，却把每日预算直接写成 `planned_minutes`；
- 没有 `estimated_task_minutes`、`completed_task_minutes`、`actual_elapsed_minutes` 三分模型；
- “不懂/为什么”不会进入持久化补救栈，也没有保存和恢复主路线位置；
- 当前 App 中完整学习流入口被未提交修改移除，旧浏览器测试仍寻找 `nav-flow`，已与真实 UI 不一致。

因此，任务开始时的完整链路判定为：**部分可用，不可声称完成**。

## 二十项逐项审计

### 1. 文件上传目前是否真实可用

**部分可用。** `POST /api/workspaces/{workspace_id}/sources/upload` 会接收真实 bytes、限制 5 MB、保存到 `data/uploads` 并调用真实解析器。扫描 PDF/空正文会明确失败。ZIP 导入成功后会清理原 ZIP 和解压成员，所以不满足所有上传资料统一持久保存。前端普通上传接真实 API，但只显示泛化结果。

### 2. 支持哪些文件格式

直接上传真实支持：PDF、DOCX、MD、TXT、HTML/HTM。前端还声明 `.markdown`，但直接上传后端不接受，存在契约不一致。ZIP/本地路径另支持若干代码、JSON、YAML、XML、CSV、IPYNB；PPTX、XLSX、EPUB 等仅有未接入的转换适配器，不能宣称产品支持。

### 3. 是否保存原始文件及哈希

**部分。** 直接上传保留原始文件，但数据库 `content_hash` 是解析正文哈希，不是原始 bytes SHA-256；无统一的文件大小、MIME、原始文件 SHA 字段。ZIP 原件不持久保存。

### 4. 是否真正解析正文

**是。** PDF 使用 PyMuPDF、DOCX 使用 python-docx、HTML 使用 BeautifulSoup、MD/TXT 读取文本；不是固定演示文案。解析失败会返回失败，扫描 PDF 返回需要 OCR，不伪装成功。

### 5. 是否产生可追溯 chunk

**部分。** chunk 真实持久化并含 `source_id`、顺序、页码、heading、正文和内容哈希；缺少段落号、`char_start`、`char_end`。现有空行切分器的 `size=900` 参数未真正限制超长单段。

### 6. 是否存在向量或关键词检索

**存在关键词检索，无向量检索。** `retrieval_service.py` 使用 BM25；依赖不可用时降级为词命中。结果按 workspace 隔离并携带来源、chunk、页码、heading、quote。

### 7. 回答是否能精确引用原文、页码或段落

**部分。** 引用校验会确认 chunk 归属、页码和 quote 确实出现在正文，Citation ORM 可持久化；能引用页码或 heading/quote，但缺段落号和字符范围。冲突表存在，但未接入检索回答链。

### 8. 是否真正生成知识点

**部分。** `knowledge_map.py` 会从真实 chunk/heading 确定性生成节点并带来源；更接近“一段一个节点”，缺难度、预计任务分钟、掌握度、验收方式等完整知识点字段。

### 9. 知识点之间是否具有前置依赖关系

**形式上有，语义不足。** 同一资料中相邻 chunk 被自动连为 prerequisite，不是根据明确课程关系或内容语义验证的前置关系。

### 10. “知识图谱”是真数据结构还是仅有界面

**核心是真数据结构，但当前入口断开。** ORM 有版本、节点、边表，service 可持久化；同时计划 payload 还维护另一份线性 UI map，形成双轨。审计实测知识地图聚焦测试为 2 failed / 23 passed，两个失败都是知识地图 API 预期 200/409、实际 405。

### 11. 用户回执目前保存了哪些信息

Legacy JSON 保存目标、动机、起止日期、每日分钟、每周天数、当前水平、预期产出、学习偏好、不可用日期、偏好星期、约束和成功条件。缺“选择哪些上传资料”。ORM 镜像还会丢 `preferred_learning_style`、`constraints`、`start_date`，存在双存储不一致。

### 12. 是否根据回执生成个性化学习计划

**弱个性化。** 使用目标、截止日期、学习日和每日分钟，但主生成器只取前 12 个 chunk，未消费真实知识依赖图，也未按资料范围、用户风险和掌握度完整调度。

### 13. 每日任务时长如何计算

审计时 lesson 时长主要是 `min(45, max(20, minutes_per_day))`，每天通常仅一个不超过 45 分钟的任务；`study_day.planned_minutes` 却直接写用户预算。输入 400 时会出现“计划显示 400、实际任务约 45”的虚标。独立 `planning_scheduler` 有容量/拓扑算法，但未接入主计划 API。

### 14. 是否区分任务时长和实际耗时

**不满足。** TaskORM 只有 `estimated_minutes` 和客户端可传的 `actual_minutes`；LearningRun state 有 `standard_task_minutes`，奖励不直接按停留时间，这是正确方向，但没有要求的三字段。

### 15. AI 教师是否主动推进课程

**部分。** LearningRun 有 explanation → worked example → guided → faded → independent → variant 的持久化阶段，当前工作树能在创建 run 时产生开场消息。但前端主流仍需要用户选路径/提交，缺完整的“下一步动作、今日剩余分钟、整体路线位置”状态。

### 16. 用户不理解时是否存在补救教学

**没有完整链路。** 有 misconception、remediation action 等孤立原语；普通消息中的“不懂/为什么”只在当前 phase 再次调用 tutor，不会进入专门补救状态。

### 17. 补救后是否能回到原计划

**未实现。** 没有持久化主路线快照、补救栈和恢复点；`decide_after_remediation` 存在但未被 LearningRun 主流程调用。

### 18. 掌握度是否由可验证学习结果驱动

**部分。** 不是随机数，事件可审计，独立尝试和提示会影响状态；但评估器主要检测回答中是否出现“解释、原因、例子、证据、步骤”等词，无法充分验证答案事实正确性，容易被关键词堆叠通过。

### 19. 哪些功能完整、部分、界面或占位

- 较完整：直接上传正文解析、SQLite 持久化、关键词检索、引用归属/quote 校验、目标 JSON、LearningRun/消息持久化。
- 部分：原件保存、知识图谱、计划、任务估时、主动阶段机、掌握度、刷新恢复。
- 仅界面或不可达：当前 App 中独立 KnowledgeMap/Planning/Tutor 组件存在，但主入口被移除；部分历史 E2E 对应旧 UI。
- 缺失：统一 raw hash/size、chunk 字符位置、明确资料范围、语义依赖/同义合并/环检测集成、400 分钟装箱、三类分钟、补救栈与原路线恢复、完整 UI E2E。

### 20. 当前最短可行修复路线

为保护脏工作树，采用隔离增量路线：

1. 新增独立 `active-teaching` 持久化表和 API，只在 FastAPI 主入口最小接线；
2. 统一保存原始文件 bytes、SHA-256、大小、类型、解析状态，以及含页/段落/字符范围/hash 的 chunk；
3. 从所选资料生成有来源的知识点和真实依赖表，做去重、合并、循环检测、孤立和时长检查；
4. 用拓扑顺序和每日预算装箱，明确容量不足，不再把页面停留时间当任务分钟；
5. 建立包含主路线位置、补救栈、掌握证据、下一步动作和三类分钟的持久化会话状态机；
6. 新增不覆盖旧页面的“主动教学链”入口；
7. 用 150 题资料依次执行后端、前端、API 验收和真实浏览器 E2E。
